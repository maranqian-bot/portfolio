MapingoAI 英语会话辅导平台

Mapingo 是一项 AI 英语学习服务：根据用户在地图上选择的真实地点和既往学习记录，提供更有情境感的英语会话练习。

负责范围 · 以设计为中心

负责范围

  • 负责 AI 辅导功能，并实现基于 FastAPI 的 AI 服务端
  • 集成 Azure Speech 与 OpenAI，实现发音评估和最终反馈流程
  • 稳定 React、Spring、FastAPI 之间的音频上传与响应契约
  • 完成从脚本生成、语音录制、发音评估、最终反馈到后续推荐的一体化学习流程

我不仅展示 AI 响应，还设计并实现了稳定的辅导流程，确保用户能够完整获得学习结果。

以设计为中心

Mapingo 的 AI 辅导需要把 OpenAI、Azure Speech、Spring API 和 React UI 串成一个学习流程，任何一个环节不稳定都可能中断整体体验。因此我不仅关注 AI 响应质量，也一并设计了 LLM 响应契约、浏览器间音频格式差异、multipart 上传边界，以及外部 API 的超时与 fallback。这个项目的设计重点不是单纯产出好的 AI 结果，而是让用户从脚本生成一直顺利到达最终反馈和后续推荐。

技术决策

技术决策

核心能力
格式自由度 vs 服务稳定性

优先固定响应契约，而非 Prompt 质量

即使 LLM 内容很好，只要响应格式稍有波动，Spring 和 React 就可能直接发生解析错误。因此我先严格固定 output format 和 schema，再在这个契约内提升 script 与 feedback 的质量。

之后加入 problemWords normalize 等后处理，即使字符串数组与对象数组混合，也不会破坏服务响应。

这是一个优先保证“服务能够完整消费的回答”，而非“更自然的回答”的决定。

客户端分支 vs 服务端标准化

在服务端将浏览器语音输入规范为标准格式

不同浏览器的 MediaRecorder 格式与 codec 不同，如果前端直接处理所有情况，复杂度会大幅上升。因此我在 FastAPI 中把 webm 上传转换为基于 ffmpeg 的 wav，统一为 Azure Speech 能稳定接收的输入。

同时为 pronunciation assessment 失败添加 STT fallback，即使格式不同或识别失败，整个辅导流程也不会中断。

我判断，与其让前端吸收所有输入差异，不如在服务端同时进行标准化与 fallback，更便于运营。

问题排查

问题排查

在 Mapingo 中，相比 AI 质量问题，响应格式和语音上传等边界问题更容易影响整个服务。下面是我实际解决的两个代表性问题。

LLM 响应格式变化导致解析失败

AI 会话脚本和最终反馈需要直接在页面渲染，因此响应结构稍有波动，Spring DTO 反序列化和前端显示就可能一起失败。我将提示词更严格地固定为 Role · Instruction · Context · Output Format，并加入 problemWords normalize 后处理，使字符串数组和对象数组混合时服务仍能完整消费响应。这段经历让我认识到，AI 响应首先必须具备“服务能够安全解析的结构”，其次才是“好的句子”。

React–Spring–FastAPI 语音集成错误

即使 React 中录音正常结束，若最终 chunk 尚未写入就创建文件，或 Spring 改变 multipart content type，FastAPI 的语音处理就容易失败。为此，我让 React 在录音结束、最终 File 完成后再上传；Spring 保留原始 content type，避免 FastAPI 丢失真实音频格式；同时让 FastAPI 在语音评估失败时仍返回基本结构，稳定三台服务之间的契约。最终我认识到，问题不在单一服务器中，而是分布在多个边界；只有从完整请求流程看，才能准确定位原因。

协作

协作与本项目收获

协作

  • 我将 AI 辅导功能分为入口页面、会话创建、对话进行、结果与推荐流程，先对齐职责，并在文档和 PR 说明中记录每个阶段由哪个服务负责什么。
  • 我以 PR 为单位对齐 FastAPI 响应字段、Spring DTO 和 React 页面消费结构；响应格式变更会共享给前后端同时确认。
  • 出现语音上传错误时，我把 React Network 请求、Spring multipart 日志和 FastAPI 诊断日志放在同一流程中比对，逐步缩小问题范围。
  • 为避免部署和复现受阻，我没有把 GitHub Actions、环境变量和 fallback 日志等运营要素与功能实现分开，而是一并整理。

本项目收获

通过 Mapingo，我学到 AI 功能不是简单接入模型；必须同时设计输入格式、响应契约、失败时的 fallback 以及展示给用户的说明，才能成为真正的服务。

特别是语音功能几乎不会在单一服务器内结束。只有把浏览器录音、Spring 传递、FastAPI 处理、Azure Speech 和 OpenAI 响应看作连续的边界问题，才能准确定位原因。

我也切身体会到，提前保证一条小日志或一个基本响应结构，就能显著改变整个团队的调试速度。
