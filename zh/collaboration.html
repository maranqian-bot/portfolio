协作方式

与团队协作的方式

这是我在项目推进中与团队共同遵守的协作标准。 规范驱动开发，并据此与团队统一分支策略、提交约定、Issue 管理及 PR、代码评审流程，保持一致执行。

工作流程

我不会直接开始实现功能，而是先确认需求与规范、协商工作范围，再进入实现。

1

确认 Issue · 需求

先将待实现功能、Bug 和改进事项整理为 Issue。

2

确认 · 编写 Spec 文档

先确认相关规范；若不存在，则按 spec · plan · tasks 的顺序编写。

3

协商实现范围

与团队对齐实现计划和工作范围后再开始。

4

创建分支

以最新 develop 为基准创建功能分支。

5

实现与验证

遵循既有代码风格与结构进行实现，并通过测试验证。

6

创建 Pull Request

创建聚焦单一目的的 PR，并整理变更意图。

7

应用评审后合并

处理评审评论并整理线程后再合并。

分支策略

始终从最新 develop分支创建，并使用能够体现工作内容的分支名；一个分支只包含一个目的。

分支命名

feature/{工作名称}
fix/{工作名称}
refactor/{工作名称}
docs/{工作名称}
chore/{工作名称}

遵守的规则

  • 不在进行中的工作分支上创建新分支。
  • 如果分支创建错误，则保留变更后重新以 develop 为基准创建。
  • 对于有顺序依赖的功能，在 PR 正文中注明合并顺序与依赖分支。

提交约定

确保只看提交消息也能了解变更意图，遵守 {type}({branch-name}) : {summary} 格式，并将提交拆分为便于评审的单位。

类型含义
feat新增功能
fix修复 Bug
refactor重构
style代码格式或样式变更
designUI/UX 变更
chore其他配置或文档工作
rename文件或名称变更
remove删除
build构建配置变更
# 示例
feat(feature/user-login-api) : 新增会员登录 API
fix(fix/payment-status-validation) : 修复支付状态验证错误

Issue 管理

将待实现功能、Bug 和改进事项拆分为 Issue，记录进度与完成标准，让团队能够看见工作流程。

拆分为 Issue 的标准

将功能、Bug 和改进事项分别拆成 Issue，明确工作单位。

留下的记录

在 Issue 中记录进度和完成标准，明确已完成的内容与范围。

Pull Request

PR 始终以 develop为目标创建，并按照团队模板记录相关 Issue、工作模块、变更内容、验证结果和给评审者的信息。创建 PR 前，我会自行检查以下项目。

✓工作分支是否从 develop创建（有顺序依赖时注明合并顺序与依赖分支）
✓PR 范围是否聚焦单一目的
✓是否排除了无关文件变更
✓是否与 Spec 或 Convention 冲突
✓是否完成必要的测试或构建检查
✓是否在 PR 正文留下评审者需要确认的事项

代码评审

不仅分享实现结果，还同时记录评审评论与修改内容，保留团队共同改进的过程。

评审处理原则

  • 明确将每条评论标记为已处理、暂缓或拒绝。
  • 不采纳时在评论中留下理由。
  • 将修正提交追加到原 PR 分支，并将线程标记为 resolved。

AI · 自动评审

  • CodeRabbit 等自动评审只要指出有效问题也会采纳。
  • 简单的样式警告只要不与团队规则冲突，也会尽量整理。
  • 与当前代码不符的意见会留下依据后跳过。

测试与验证

按技术栈使用以下命令验证后，将结果记录在 PR 中。只修改文档时，也会一并说明省略验证的理由。

# Backend
cd backend && ./gradlew test

# Frontend
cd frontend && npm run build

# FastAPI
cd fastapi && python -m pytest
