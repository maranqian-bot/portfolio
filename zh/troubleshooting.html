JWT 认证过滤器异常被返回为 500

PR #351
问题

调用受过期或篡改令牌保护的 API 时，返回的不是客户端预期的 401，而是 500。前端无法区分登录过期和服务器错误，重新登录提示流程因此失效。

原因

起初我以为是全局异常处理配置的问题并检查了 Controller Advice，但 JWT 验证实际上在到达 DispatcherServlet 前的 Security Filter Chain 中执行。因此过滤器内部产生的令牌过期、签名不匹配异常无法被 Controller Advice 捕获，在没有单独处理的情况下像 RuntimeException 一样继续传播，最终转换成 500。

解决方案

在 JWT 过滤器中，我将令牌验证失败原因整理为 AuthenticationException 类型，并在 AuthenticationEntryPoint 中明确返回 401 状态码和错误消息。为避免暴露过多细节，我分离了面向客户端的提示消息与服务器日志。

结果

我分别复现令牌缺失、过期和篡改请求，确认它们全部返回 401。正常令牌请求保持原有 API 流程，前端也可以依据 401 处理重新登录提示。

最终项目 · CareerWave

刷新时因 refresh 竞争而退出登录

PR #971
问题

在页面刷新或 OAuth 回调后、access token 尚未恢复到内存的瞬间，多个组件同时尝试恢复会话，导致用户立即退出登录。即使存在有效的 refresh Cookie，会话也会因进入页面的时机而中断，造成不稳定的体验。

原因

在收到 401 响应或进入初始受保护路由时，每个请求都会独立地 /token/refresh 调用，服务器同时启用了 refresh token rotation 和重复使用检测。如果使用同一个 Cookie 几乎同时发起两次以上重新签发，系统可能判断已轮换的令牌被再次使用，从而废弃整个会话。

解决方案

我将前端会话恢复逻辑合并为 single-flight，让后续请求加入正在进行的 refresh Promise。同时在 OAuth 回调页面通过 probeAuth() 固定顺序，确保 refresh Cookie 轮换完成后再跳转，关闭新页面使用旧 Cookie 再次发起 refresh 的竞争窗口。

结果

即使调用 probeAuth同时多次调用，也通过测试固定为只发出一次 refresh 请求。OAuth 回调后同样验证轮换完成前不跳转，刷新后立即退出登录的现象消失。

最终项目 · CareerWave

社交登录用户支付时返回 404

PR #825
问题

QA 发现，Kakao 社交登录用户尝试支付时，前端没有进入支付页面而是收到 404。用户无法知道支付准备失败的原因，后端也走上了与实际原因不符的异常路径。

原因

部分社交账号的邮箱为空，该值违反了 customer_email NOT NULL 约束，并在 DB 保存阶段产生了 DataIntegrityViolationException。但该异常流入原本用于恢复并发请求冲突的 catch 代码块，实际的约束违反被当成订单不存在处理，最终变成了 404。

解决方案

我在支付 INSERT 前明确验证邮箱是否存在，在前端阻止约束违反并转换为业务错误。同时修改前端错误分支和消息，将支付进入失败处理为需要补充用户信息，而不是 404。

结果

使用没有邮箱的社交账号重新复现支付路径时，不再被误判为 404。QA 阶段用于确认原因的 DB 直接查询结果与响应流程保持一致，用户也能收到正确的支付失败原因。

LLM 响应格式变化导致解析失败

PR #16
问题

AI 会话脚本和最终反馈需要直接在页面渲染，因此字段结构稍有变化，服务解析就会失败。即使再次调用同一功能，只要响应键名或数组结构发生波动，Spring DTO 反序列化和前端显示就会同时失败。

原因

LLM 是自然语言模型，提示词宽松时可能产生说明句、不必要的包装文本或缺失键等格式偏差。服务层假定响应是结构化 JSON，因此模型输出规范不足时，解析失败会直接变成功能失败。

解决方案

我将提示词拆分为 Role · Instruction · Context · Output Format，明确模型必须遵守的输出契约。将响应结构限制在 JSON Schema 级别，并依据 Spring DTO 与页面所需字段收窄允许值，使服务层即使面对格式波动也能稳定接收。

结果

我开始优先关注 AI 响应是否具有服务可以完整消费的结构，而不是句子对人是否听起来自然。脚本生成、反馈生成和推荐后续处理共享同一响应契约后，传递到页面的失败大幅减少。

迷你项目 · Mapingo

外部 AI API 错误中断整个辅导

PR #14
问题

发音评估和最终反馈需要连续调用 Azure Speech 与 OpenAI，因此任何一步发生 Timeout 或解析错误，都可能让整个辅导以 500 中断。用户即使成功输入语音，也可能收不到结果页面，或因推荐阶段失败而丢失之前的反馈。

原因

初始管线强烈假定外部 API 响应正常，失败时异常向上冒泡并中断整个流程。Azure 识别失败、OpenAI 响应 JSON 解析错误和推荐后续处理失败，本应是独立的局部失败，却都扩大成了整个辅导失败。

解决方案

我在 FastAPI 增加发音评估端点诊断日志和异常路径日志；Azure 识别失败时，改为用 STT fallback 文本和基础反馈组装响应。OpenAI 分析由 safe wrapper 包裹，失败时返回空的 problemWords 和默认消息；即使推荐阶段失败，也保留之前生成的最终反馈，并拆分 Spring 侧流程。

结果

即使部分外部 API 失败，用户也能获得最低限度的反馈和下一步信息。日志会记录失败阶段，响应则尽可能保留学习结果，从而降低整个辅导中断的频率。

迷你项目 · Mapingo

浏览器录音格式不同导致发音识别失败

PR #13
问题

用户直接上传浏览器录制的语音时，某些环境可以完成发音评估，另一些环境却会立即失败。用户明明已正常授予麦克风权限并完成录音，却无法识别语音。

原因

不同浏览器和设备的 MediaRecorder 格式与 codec 不同，而 Azure Speech 对输入格式差异很敏感。服务假定上传语音总是同一格式，因此 WebM 文件或采样率差异会直接导致识别失败。

解决方案

在 FastAPI 中将上传语音转换为基于 FFmpeg 的 16kHz mono WAV，统一发音评估输入。Azure 发音评估失败时返回 STT fallback 和基础反馈，即使格式有问题或输入质量较低，辅导流程也不会完全中断。

结果

浏览器间的输入差异不再直接变成服务故障；在不同录音环境下也能获得最低限度的语音评估结果。即使语音无法完美评估，用户体验也从“失败”变成了“受限结果”。

迷你项目 · Mapingo

React–Spring–FastAPI 语音集成错误

PR #152
问题

即使用户录音在 React 中正常结束，经过 Spring 传到 FastAPI 时仍会反复出现上传失败，或响应已返回但前端播放、显示中断的问题。即使三台服务器都正常运行，边界契约稍有偏差，辅导链路也很容易断裂。

原因

前端在录音结束后、最终 chunk 尚未收集完成前就传递 Blob，部分请求的 File 元数据不完整。Spring 侧将 multipart 语音部分统一转换为 application/octet-stream发送，丢失原始 content type 信息，导致 FastAPI 无法获得解析语音文件所需的提示。

解决方案

我修改 React，使其在录音结束并收集完所有 chunk 后完成 File 对象再上传，并在入口阻止空录音数据。Spring 的 FastAPI 客户端改为保留 MultipartFile.getContentType()并放入 multipart 部分发送；同时让 FastAPI 在语音评估失败时保持基础结构，稳定三台服务器之间的契约。

结果

从录音、上传、发音评估、反馈响应到播放的链路稳定地连成一体。实际提交中依次落实了前端 recorder 文件确认、Spring content type 保留和 FastAPI fallback 响应增强，减少了集成错误。

招聘公告列表 API：平均响应时间从 15.6 秒缩短至 1.1 秒

PR #951
问题

GET /api/v1/user/job-notices 不仅返回列表数据，还一次性返回 5 种筛选选项和 2 种统计结果。因此即使是未登录的单次请求也会执行 8～9 个 DB 查询；在 10 万条数据的 JMeter 压力测试中，平均响应时间达到 15,551ms、p95 为 28,654ms、TPS 仅 6.3/s、错误率为 1.11%。

原因

瓶颈不在一次简单的列表查询，而在 createFilterOptions() 的 5 个 Distinct 查询，以及 countActiveJobNotices()、countTodayNewActiveJobNotices() 在每次请求中重复执行的结构。此外，ACTIVE 公告查询路径没有合适的索引，很可能执行 Sequential Scan，变更频率低的聚合成本与排序成本同时累积。

解决方案

首先将缓存目标方法拆分到独立的 Spring Bean JobNoticeCacheService，避免因 self-invocation 导致 @Cacheable 失效。我为筛选选项设置 1 小时 TTL、为统计设置 5 分钟 TTL 并应用 Redis 缓存。由于招聘公告由 scraper 直接写入 DB，我没有使用 @CacheEvict，改为 TTL 过期策略。同时在 PostgreSQL 中增加仅索引 ACTIVE 公告的部分索引，使实际查询目标不受 CLOSED 数据累积影响而更快命中。

结果

最终，10 万条数据下平均响应时间从 15,551ms 降至 1,118ms，p95 从 28,654ms 降至 1,385ms，TPS 从 6.3/s 提升至 85.2/s。错误率也从 1.11% 降至 0.00%；根据 EXPLAIN ANALYZE，列表查询路径从 Sequential Scan 转为以 Index Scan 为主。也就是说，通过缓存减少重复聚合，并用部分索引缩小 ACTIVE 查询范围，从结构上稳定了列表 API。

招聘公告 100 万条列表查询：后页响应时间从 84 秒缩短至 0.137 秒

PR #1292
问题

招聘公告数据增至约 100 万条后，基于 OFFSET 的列表查询越到后页越慢。尤其在 deep page，DB 丢弃前几十万行的成本高于实际用户请求，响应从几秒上升到几十秒。

原因

原查询先排序全部行，再跳过 OFFSET 数量的行，因此越到后页，被丢弃行的成本累积越多。此外排序相同值时没有 tie-breaker，页面边界可能重复或遗漏；如果第一阶段查询与实际组装响应之间数据发生变化，结果一致性也会动摇。

解决方案

在保持 API 契约不变的前提下，先通过覆盖索引快速取出页面所需的 ID，再读取这些 ID 对应的实际行，改为 deferred join 两阶段方案。同时在所有排序中加入 jobNoticeId tie-breaker，并在第二阶段查询中再次应用相同 predicate，确保 deep pagination 下顺序和结果一致性不受影响。

结果

根据 EXPLAIN ANALYZE，OFFSET 50 万的位置从约 84 秒降至约 137ms，80 万的位置也稳定在约 147ms 而不再超时。不改造前端 API，仅精准移除 deep page 瓶颈，同时保住了性能与原有 UX。

订阅自动支付批处理：1 万条处理时间从 64.4 秒缩短至 17.5 秒

PR #1281
问题

自动支付批处理会随着目标订阅增加而逐条重新查询所需信息，并顺序等待 Toss 支付调用。批量变大不仅会延长完成时间，也会增加调度器推迟下一项任务的风险。

原因

订阅、套餐、支付资料、会员信息和幂等支付信息都在循环中逐条查询，形成典型的 N+1 模式。外部支付 API 也按顺序调用，DB 瓶颈和网络等待同时拉长了 wall-clock 时间。

解决方案

在批处理开始前，将所需关联数据通过 IN 批量查询预加载到 RenewalContext 中，支付创建也复用预加载结果。在此基础上使用固定线程池进行 bounded 并行化，同时加入幂等键、单笔超时和取消处理，在提速的同时防止重复支付与调度器阻塞。

结果

每笔 SQL 从 10 个降至 6 个，支付进入前的重复查询从约 3 万次缩减为实际上个位数的批量查询。1 万条的 wall-clock 从 64.4 秒降至 17.5 秒；即使 Toss 存在延迟，也从 235.6 秒降至 13.9 秒，同时保持支付准确性不变。
