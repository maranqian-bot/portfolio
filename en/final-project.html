Decisions

Technical decisions

Core capabilities
Availability vs security

Role-based policy during Redis failures

黑名单查询失败时可以阻断所有用户，但这会导致大量普通用户被强制退出；全部放行则可能让高权限账户绕过安全检查，风险同样很高。

因此，普通用户优先保证可用性而放行，管理员则优先保证安全性而拒绝。

这个决定基于一个原则：即使是同一种故障，也不必对所有用户采用相同策略。

Redis (temporary) + DB (authoritative)

分开保存登录失败次数与账户锁定状态

I separated login-failure data by its purpose instead of placing everything in one store. Attempt counts belong in Redis because they are high-frequency and should expire by TTL; account-lock state belongs in the database because it must survive restarts and Redis outages.

This keeps already-locked accounts locked even when Redis is unavailable, while temporary attempt counts can accumulate quickly and be cleaned up automatically.

The split is based on whether a state may disappear or must be retained, rather than on technology preference.

Convenience vs exposure risk

billingKey 不仅加密保存，还从序列化路径中结构性排除

billingKey is highly sensitive payment data: exposure could enable unauthorized charges. AES encryption alone is not sufficient because encrypted values can still be accidentally serialized or logged.

I applied AES encryption at rest and used @Getter(AccessLevel.NONE) with a dedicated accessor so billingKey is structurally excluded from Jackson serialization candidates.

The key principle is to protect sensitive data not only at rest, but also by minimizing every path through which it could leak accidentally.

Generated queries vs complex-query separation

Separate JPA Repository and QueryRepository responsibilities

I did not force every read through one pattern: simple duplicate checks and single-row lookups use JPA Repository methods, while multi-table and complex queries use a dedicated QueryRepository.

Putting simple reads into a complex query layer makes the code heavy; forcing complex joins into method-name repositories hides intent and hurts maintainability.

This was a complexity-based separation of responsibilities, not an arbitrary push for one uniform approach.

Troubleshooting

Troubleshooting

Deep-pagination performance issue

招聘数据扩展到 100 万条后，列表 API 在深分页区间响应急剧变慢。起初我误以为负载测试中的延迟是缓存问题，实际瓶颈来自 OFFSET 本身。通过 EXPLAIN ANALYZE 重新确认执行计划后，应用 ACTIVE 职位覆盖索引与 deferred join 解决了问题。This taught me to locate bottlenecks using reproducible metrics rather than intuition or noisy load-test observations.

404 payment issue for social-login users

另一个案例是 Kakao 登录用户发起支付时才出现 404。直接查询数据库发现部分社交登录用户邮箱为空，订单创建时的 NOT NULL 约束异常被错误地吸收到重复请求 catch 逻辑中。随后增加 INSERT 前校验、拆分异常处理，并同步修正前端状态码分支。I learned that identical-looking errors can have different causes, and that data-constraint violations are safer to stop with pre-validation.

Lessons learned

通过这个项目，我比单纯实现功能更清晰地建立了稳定运营服务的设计标准。

我学到性能与稳定性应以日志、执行计划、响应时间等可复现指标验证，而不是凭感觉判断。

我也切身体会到，越是包含外部支付商或社交登录等不可控因素，越要在早期设计中同时考虑 fallback 与异常处理。

尤其在认证和支付等敏感领域，不能只实现正常流程，还必须确保失败时服务链路不会中断。
