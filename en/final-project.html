Recovery

Auth Flow

Authentication, sessions & social login

I focused on maintaining sessions after login and reliably linking social accounts to existing member records.

Auth · Session
  • Access Token · Refresh Token dual-token structure
  • Immediate logout invalidation with a Redis JTI blacklist
  • Store only SHA-256 hashes of refresh tokens
  • Limit each user to five concurrent sessions
  • Session idle timeout
  • Control repeated attempts with login IP rate limits
Social Login
  • Integrate Kakao, Naver, and Google OAuth
  • Separate the additional-information step for social signup
  • Link existing accounts and show the last login method
  • Use short-lived cookies to address CWE-598
Billing Flow

Subscription & payment consistency

I handled subscription lifecycle and payment settlement as one flow so subscription status, entitlements, and usage remain consistent after payment.

Subscription
  • Subscription lifecycle from plan selection to activation, cancellation, and expiration
  • Issue and manage one-time free entitlements per product
  • Expose monthly usage, utilization, and subscription status
Payment
  • Process payment, subscription, entitlement, and usage changes in one transaction
  • Persist Toss failure records independently with REQUIRES_NEW
  • Prevent duplicate payments with orderId, idempotencyKey, and paymentKey
  • Encrypt billingKey with AES and exclude it from serialization paths

Decisions

Technical decisions

Core capabilities
Availability vs security

Role-based policy during Redis failures

Blocking everyone when blacklist lookup fails could force ordinary users out at scale; allowing everyone could let privileged accounts bypass security.

I therefore allow ordinary users for availability, but deny administrators for security.

The principle: the same failure does not require the same policy for every user.

Redis (temporary) + DB (authoritative)

Store login-failure counts and account-lock state separately

I separated login-failure data by purpose: attempt counts belong in Redis because they expire by TTL, while account-lock state belongs in the database because it must survive restarts and Redis outages.

This keeps locked accounts protected when Redis is unavailable, while temporary attempt counts can be accumulated and cleaned up quickly.

The storage split is based on whether a state may disappear or must be retained, not on technology preference.

Convenience vs exposure risk

Encrypt billingKey and structurally exclude it from serialization paths

billingKey is highly sensitive payment data: exposure could enable unauthorized charges. AES encryption alone is insufficient because encrypted values can still be accidentally serialized or logged.

I applied AES encryption at rest and used @Getter(AccessLevel.NONE) with a dedicated accessor to exclude billingKey from Jackson serialization candidates.

The key principle is to protect sensitive data at rest and minimize every path through which it could leak accidentally.

Generated queries vs complex-query separation

Separate JPA Repository and QueryRepository responsibilities

I use JPA Repository methods for simple checks and lookups, and a dedicated QueryRepository for multi-table, complex queries.

A complex query layer would make simple reads too heavy, while method-name repositories would hide complex join intent and hurt maintainability.

This is a complexity-based separation of responsibilities, not forced uniformity.

Troubleshooting

Troubleshooting

Deep-pagination performance issue

After expanding job data to one million rows, the listing API slowed sharply on deep pages. I initially suspected cache synchronization, but OFFSET itself was the bottleneck. EXPLAIN ANALYZE confirmed the plan; a covering index for ACTIVE jobs and deferred join solved the issue.This experience taught me to locate bottlenecks with reproducible metrics instead of intuition or load-test noise.

404 payment issue for social-login users

Another issue was a 404 that occurred only when Kakao-login users attempted payment. A database check found missing emails for some social-login users, while a NOT NULL violation was incorrectly absorbed by duplicate-request handling. I added pre-insert validation, separated exception handling, and fixed the frontend status branch.I learned that similar-looking errors can have different causes, and that data-constraint violations should be stopped with pre-validation.

Collaboration & lessons learned

Collaboration

  • I align requirements and ownership in documentation first, record changes before implementation, and keep the team working from one shared standard.
  • I link issue branches to PR descriptions, record intent and scope, and apply CodeRabbit and team-review feedback as follow-up commits so decisions remain traceable in code.
  • I align the API contract with the frontend through Spec, Swagger, DTOs, and TypeScript types, and use ApiResponse across authentication and billing to reduce rework.
  • For QA issues, I inspect the database, logs, and frontend behavior together to narrow the root cause.

Lessons learned

This project gave me clearer design standards for operating reliable services, beyond simply implementing features.

I learned to validate performance and stability with reproducible metrics such as logs, execution plans, and response times.

The less controllable an integration is, such as payments or social login, the earlier fallback and exception handling must be designed.

In sensitive domains such as authentication and payments, the service flow must remain intact even when the happy path fails.
