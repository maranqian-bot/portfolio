Problem Solving and Diagnosis

A record of reproducing problems and narrowing down their causes

I documented the problems I encountered while working on Mapingo AI conversation coaching and CareerWave authentication and payment domains, organized by reproduction conditions, cause analysis, solutions, and revalidation.

Final Project · CareerWave

JWT authentication-filter exception returned as 500

PR #351
Problem

When an API protected by an expired or tampered token was called, it returned 500 instead of the 401 the client expected. The frontend could not distinguish an expired login from a server error, so the re-login guidance flow broke.

Cause

I initially suspected the global exception-handling configuration and checked Controller Advice, but JWT validation actually ran in the Security Filter Chain before reaching DispatcherServlet. Token-expiration and signature-mismatch exceptions raised inside the filter could not be caught by Controller Advice; without dedicated handling, they propagated like RuntimeException and became 500.

Solution

In the JWT filter, I normalized token-validation failures as AuthenticationException types and explicitly returned the 401 status code and error message from AuthenticationEntryPoint. I separated client-facing guidance from server logs to avoid exposing excessive detail.

Result

I reproduced missing-token, expired-token, and tampered-token requests separately and confirmed that all returned 401. Valid-token requests kept the existing API flow, and the frontend could use 401 to show the re-login guidance.

Final Project · CareerWave

Logout caused by a refresh race on page reload

PR #971
Problem

At the moment after a page reload or OAuth callback when the access token had not yet been restored to memory, multiple components tried to restore the session at once and logged the user out. Even with a valid refresh Cookie, the session could be interrupted by page-entry timing, creating an unstable UX.

Cause

When a 401 response was received or an initial protected route was entered, each request independently /token/refresh called the endpoint, while the server applied refresh-token rotation and reuse detection. If the same Cookie triggered two or more nearly simultaneous reissues, the system could treat the rotated token as reused and revoke the entire session.

Solution

I grouped the frontend session-restoration logic into a single-flight so later requests join the refresh Promise already in progress. On the OAuth callback page, I also used probeAuth() to enforce the order and wait for refresh Cookie rotation before navigating, closing the race window in which a new page could refresh again with the old Cookie.

Result

Even if probeAuth is called multiple times concurrently, tests guarantee that only one refresh request is sent. We also verify that navigation waits for rotation after OAuth callbacks, eliminating the immediate logout after reload.

Final Project · CareerWave

404 returned when a social-login user pays

PR #825
Problem

QA found that when a Kakao social-login user attempted payment, the frontend received 404 instead of entering the payment page. The user could not see why payment preparation failed, and the backend followed an exception path unrelated to the actual cause.

Cause

Some social accounts had an empty email, which violated the customer_email NOT NULL constraint and produced the following during DB persistence: DataIntegrityViolationException.The exception then flowed into a catch block originally intended to recover from concurrent-request conflicts. The actual constraint violation was treated as a missing order and became 404.

Solution

I explicitly validated email presence before the payment INSERT, blocking the constraint violation at the frontend and converting it into a business error. I also updated the frontend error branch and message so payment-entry failure is handled as a need for additional user information, not 404.

Result

When the payment path was reproduced with a social account missing an email, it was no longer misidentified as 404. The DB lookup used during QA and the response flow now agree, and users receive the correct reason for payment failure.

Mini Project · Mapingo

Parsing failure caused by an LLM response-format change

PR #16
Problem

AI conversation scripts and final feedback had to render directly on the page, so even a small field-structure change caused service parsing to fail. Even when the same feature was called again, a change in response keys or array structure could break both Spring DTO deserialization and frontend rendering.

Cause

Because an LLM is a natural-language model, a loose prompt can produce format deviations such as explanations, unnecessary wrapper text, or missing keys. The service layer assumed structured JSON, so weak output rules turned parsing failures directly into feature failures.

Solution

I split the prompt into Role · Instruction · Context · Output Format to make the output contract explicit. I constrained the response structure to JSON Schema level and narrowed allowed values around the fields expected by the Spring DTO and page, allowing the service layer to receive responses reliably despite format variation.

Result

I began prioritizing whether an AI response had a structure the service could consume end-to-end, rather than whether its sentences sounded natural. Sharing one response contract across script generation, feedback generation, and recommendation follow-up greatly reduced failures reaching the page.

Mini Project · Mapingo

An external AI API error interrupted the entire coaching flow

PR #14
Problem

Pronunciation assessment and final feedback called Azure Speech and OpenAI sequentially, so a Timeout or parsing error at any step could stop the entire coaching flow with 500. Even after successful voice input, users might receive no result page or lose earlier feedback when the recommendation step failed.

Cause

The initial pipeline strongly assumed external API responses were normal; failures bubbled upward and interrupted the whole flow. Azure recognition failure, OpenAI response-JSON parsing errors, and recommendation follow-up failures should have been independent partial failures, but each expanded into a complete coaching failure.

Solution

I added pronunciation-assessment endpoint diagnostics and exception-path logs in FastAPI. When Azure recognition fails, the response is assembled from STT fallback text and basic feedback. OpenAI analysis is wrapped in a safe wrapper that returns empty problemWords and a default message on failure; the Spring flow is also separated so earlier final feedback is preserved even if recommendations fail.

Result

Users can still receive minimum feedback and next-step information when part of an external API fails. Logs record the failed stage while responses preserve as much learning output as possible, reducing complete coaching interruptions.

Mini Project · Mapingo

Browser recording formats caused pronunciation-recognition failures

PR #13
Problem

When users uploaded browser-recorded audio directly, pronunciation assessment worked in some environments but failed immediately in others. Users had granted microphone permission and recorded normally, yet speech could not be recognized.

Cause

MediaRecorder formats and codecs differ across browsers and devices, while Azure Speech is sensitive to input-format differences. The service assumed uploaded audio would always have one format, so WebM files or sampling differences directly caused recognition failures.

Solution

In FastAPI, I converted uploaded audio to FFmpeg-based 16kHz mono WAV to standardize pronunciation-assessment input. When Azure pronunciation assessment fails, STT fallback and basic feedback are returned so format problems or low-quality input do not completely interrupt coaching.

Result

Differences between browser inputs no longer become service failures directly, and different recording environments still produce a minimum assessment result. Even when audio cannot be assessed perfectly, the user experience changes from “failure” to a “limited result.”

Mini Project · Mapingo

React–Spring–FastAPI voice-integration error

PR #152
Problem

Even when recording ended normally in React, uploads could fail while passing through Spring to FastAPI, or the frontend could stop playing or displaying a returned response. The coaching chain could break from a small boundary-contract mismatch even when all three servers were healthy.

Cause

The frontend passed a Blob immediately after recording ended, before collecting the final chunk, and some requests had incomplete File metadata. Spring converted the multipart audio part to application/octet-stream before sending, which lost the original content type and left FastAPI without the hint needed to interpret the audio file.

Solution

I changed React to complete the File object after recording ended and all chunks were collected, then upload it; empty recordings are blocked at the entry point. The Spring FastAPI client now preserves MultipartFile.getContentType() and sends it in the multipart part; FastAPI also keeps a base structure when voice assessment fails, stabilizing the contract across the three servers.

Result

The flow from recording and upload through pronunciation assessment, feedback response, and playback is now stable end-to-end. The commits successively finalized the recorder file in the frontend, preserved content type in Spring, and strengthened FastAPI fallback responses, reducing integration errors.

Final Project · CareerWave

Job-list API: average response time reduced from 15.6s to 1.1s

PR #951
Problem

GET /api/v1/user/job-notices It returned not only list data but also five filter options and two statistics in one response. Even one unauthenticated request therefore executed 8–9 DB queries; in a JMeter test with 100,000 records, average latency reached 15,551ms, p95 28,654ms, TPS only 6.3/s, and error rate 1.11%.

Cause

The bottleneck was not one simple list query, but createFilterOptions() five Distinct queries from it, plus countActiveJobNotices(), countTodayNewActiveJobNotices(), a structure that repeated them on every request. The ACTIVE job path also lacked a suitable index and was likely to use Sequential Scan, accumulating both low-change aggregation cost and sorting cost.

Solution

I moved cache-target methods into a separate Spring Bean JobNoticeCacheService to prevent self-invocation from disabling @Cacheable. I applied Redis caching with a one-hour TTL for filters and five minutes for statistics. Because the scraper writes jobs directly to the DB, I did not use @CacheEvict; I used TTL expiration instead. I also added a partial PostgreSQL index for ACTIVE jobs so actual query targets are faster regardless of accumulated CLOSED data.

Result

Ultimately, with 100,000 records, average latency fell from 15,551ms to 1,118ms, p95 from 28,654ms to 1,385ms, and TPS rose from 6.3/s to 85.2/s. Error rate fell from 1.11% to 0.00%; EXPLAIN ANALYZE showed the list path switching from Sequential Scan to primarily Index Scan. Caching removed repeated aggregation and a partial index narrowed ACTIVE queries, structurally stabilizing the API.

Final Project · CareerWave

One-million job-list query: deep-page response time reduced from 84s to 0.137s

PR #1292
Problem

After job data grew to about one million rows, OFFSET-based list queries became slower on later pages. On deep pages, the DB cost of discarding hundreds of thousands of earlier rows exceeded the actual request cost, pushing latency from seconds into tens of seconds.

Cause

The original query sorted all rows and then skipped OFFSET rows, so discarded-row cost accumulated on later pages. There was also no tie-breaker for equal sort values, allowing duplicates or omissions at page boundaries; changes between the first query and response assembly could also undermine consistency.

Solution

Without changing the API contract, I first used a covering index to fetch only the IDs needed for the page, then read the corresponding rows using a two-stage deferred join. I also added jobNoticeId as a tie-breaker and reapplied the same predicate in the second-stage query so order and consistency remain stable during deep pagination.

Result

According to EXPLAIN ANALYZE, the 500,000-offset point fell from about 84s to about 137ms, and the 800,000-offset point stabilized around 147ms instead of timing out. I removed only the deep-page bottleneck without replacing the frontend API, preserving both performance and the existing UX.

Final Project · CareerWave

Subscription auto-payment batch: 10,000-item processing reduced from 64.4s to 17.5s

PR #1281
Problem

The auto-payment batch re-queried required information one subscription at a time and waited for Toss calls sequentially. Larger batches took longer to finish and increased the risk of delaying the scheduler’s next task.

Cause

Subscriptions, plans, payment profiles, member data, and idempotent-payment data were queried individually inside the loop, creating a typical N+1 pattern. External payment APIs were also called sequentially, so DB bottlenecks and network waits both extended wall-clock time.

Solution

Before the batch started, I preloaded related data through IN batch queries into RenewalContext; payment creation reused those results. I then applied bounded parallelism with a fixed thread pool, adding idempotency keys, per-payment timeouts, and cancellation handling to increase speed while preventing duplicate payments and scheduler blocking.

Result

SQL statements per item fell from 10 to 6, and repeated pre-payment lookups shrank from about 30,000 to effectively single-digit batch queries. For 10,000 items, wall-clock time fell from 64.4s to 17.5s; even with Toss latency it fell from 235.6s to 13.9s, while payment accuracy remained unchanged.
