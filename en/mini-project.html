Responsibilities · Design-led

Responsibilities

  • Owned AI Coaching features and implemented the FastAPI-based AI server.
  • Integrated Azure Speech and OpenAI to deliver pronunciation assessment and the final-feedback flow.
  • Stabilized the audio-upload flow and response contract across React, Spring, and FastAPI.
  • Completed one learning flow from script generation and voice recording through pronunciation assessment, final feedback, and follow-up recommendations.

I did more than display AI responses: I designed and implemented a stable coaching flow so users could complete the learning journey and receive results.

Design-led

Mapingo’s AI Coaching had to connect OpenAI, Azure Speech, the Spring API, and the React UI into one learning flow. Instability at any point could interrupt the whole experience. I therefore designed not only for response quality, but also for the LLM response contract, browser-specific audio-format differences, multipart upload boundaries, and external API timeouts and fallbacks. The goal was not simply a good AI result, but a journey that reliably carries users from script generation to final feedback and follow-up recommendations.

Technical Decisions

Technical Decisions

Core Capability
Format Flexibility vs Service Stability

Prioritize a Fixed Response Contract over Prompt Quality

Even when LLM content is good, small variations in response format can cause parsing errors in Spring and React. I first fixed the output format and schema strictly, then improved script and feedback quality within that contract.

I then added post-processing such as problemWords normalization so mixed string arrays and object arrays would not break the service response.

This was a decision to prioritize an answer the service can consume end-to-end over a more natural-sounding answer.

Client-side Branching vs Server-side Standardization

Standardized browser voice input to a common format on the server.

MediaRecorder formats and codecs differ across browsers; handling every case directly on the frontend would sharply increase complexity. In FastAPI, I converted webm uploads to ffmpeg-based wav so Azure Speech received a stable, unified input.

I also added an STT fallback for pronunciation-assessment failures, so format differences or recognition failures would not interrupt the coaching flow.

I concluded that standardizing and applying fallbacks on the server was more maintainable than making the frontend absorb every input difference.

Troubleshooting

Troubleshooting

In Mapingo, boundary issues such as response format and voice upload were more likely than AI-quality issues to destabilize the entire service. These are two representative problems I solved.

Parsing Failures Caused by Changes in LLM Response Format

AI conversation scripts and final feedback had to render directly on screen, so even small response-structure changes could break both Spring DTO deserialization and frontend display. I fixed the prompt more strictly as Role · Instruction · Context · Output Format and added problemWords normalization, allowing the service to consume responses even when string arrays and object arrays were mixed.This taught me that an AI response must first have a structure the service can parse safely, and only then be a good sentence.

React–Spring–FastAPI Voice Integration Errors

Even when recording ended normally in React, voice processing in FastAPI could fail if the file was created before the last chunk was written or if Spring changed the multipart content type. I made React upload only after recording ended and the final File was complete; Spring preserved the original content type so FastAPI would not lose the real audio format; and FastAPI retained a base response structure even when voice assessment failed, stabilizing the contract across all three services.I ultimately learned that the problem was not inside one server but distributed across multiple boundaries; only the complete request flow made precise diagnosis possible.

Collaboration

Collaboration and What I Learned

Collaboration

  • I divided AI Coaching into entry screens, session creation, conversation, and results/recommendation flows; aligned responsibilities first; and documented which service owned what at each stage in the docs and PR descriptions.
  • I aligned FastAPI response fields, Spring DTOs, and the React consumption structure per PR; changes to response formats were shared for frontend and backend confirmation at the same time.
  • When voice-upload errors occurred, I compared React Network requests, Spring multipart logs, and FastAPI diagnostic logs in one flow to narrow the issue step by step.
  • To prevent deployment and reproduction from being blocked, I organized operational elements such as GitHub Actions, environment variables, and fallback logs together with the feature implementation.

What I Learned from This Project

Through Mapingo, I learned that AI features are not simply model integration. Input formats, response contracts, failure fallbacks, and user-facing guidance all need to be designed together before they become a real service.

Voice features in particular rarely end within one server. Accurate diagnosis required treating browser recording, Spring handoff, FastAPI processing, Azure Speech, and OpenAI responses as one continuous boundary problem.

I also experienced firsthand how guaranteeing one small log line or one base response structure in advance can materially change the whole team’s debugging speed.
